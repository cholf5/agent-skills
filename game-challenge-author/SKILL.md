# Game Challenge Author

把"教程 / 源码"压缩成一份 AI Agent 能直接照着实现、全程不需要查外部资料的题目文档。

## 适用场景与输入形态

| 输入 | 说明 |
|---|---|
| 教程文档 | step-by-step 教程（可能多文件、带操作截图），规则和数值藏在操作步骤里 |
| 参考源码 | 一份可运行的完整游戏实现，作为权威事实来源 |
| 资产目录 | 图片/音频/字体等，题目必须引用它们 |
| 目标引擎 | 可能已知（如 godot），也可能未知（测试者临时指定任意引擎） |

## 核心理念（为什么这么设计）

1. **单一自包含文件**。AI 读一遍就拿到全部信息；拆成多文件会漏读、来回跳。题目通常 200 行左右。
2. **引擎无关核心 + 引擎附录**。测试者可能指定任意引擎（godot / unity / ue / defold / love2d / monogame / cocos-creator / blazor wasm…）。行为规格用引擎无关语言写；引擎专属映射（场景树、信号、API 参数）收进附录，只有用该引擎的 AI 才读。
3. **数值全部显式化**。教程最大的坑：数值藏在操作步骤里（"把这个 Timer 设为 0.5"）或压根没写（动画帧率、显示缩放、碰撞尺寸）。所有影响行为的数字都要进表格；写完后自问"还有哪里需要猜？"
4. **参考实现 > 教程文字**。教程含糊或写错的地方（例如教程说缩放 0.75，参考源码实际 0.5），以能跑通的参考实现为准。
5. **验收清单写可观察行为**。AI 要能对着清单逐项运行验证，所以只写"玩家出现在 (240, 450)"这类可观察事实，不写实现细节。
6. **预判踩坑点**。把 AI 常见卡点提前写进题目：音频格式兼容（ogg 在 MonoGame 默认管线 / Safari Web Audio 不支持）、编辑器元数据文件（如 Godot 的 `*.import`）不要复制、物理回调中禁用碰撞要延迟、BGM 须开循环、启动场景要设置、字体许可证随字体复制等。

## 工作流程

### 1. 收集输入

定位并通读全部教程文档、参考源码、资产目录；记录文件清单。教程和源码都有时，源码是权威。

### 2. 提取数值

从教程 + 源码中提取所有参数，分类列成表：

- 画面/窗口：视图尺寸、拉伸/缩放方式、背景
- 输入：动作名、按键、附加按键（如 WASD）
- 实体：速度、出生点、动画帧/帧率、显示缩放、碰撞形状与尺寸
- 计时：生成间隔、计分间隔、开局延迟、消息时长
- 流程：完整状态机（标题 → 开局 → 游戏 → 结束 → 重开），每步的界面与实体变化
- 音频：BGM 循环、音效触发时机
- 资产：每个文件的用途、在题目中的引用名

### 3. 消除歧义、补全隐含步骤

- 教程含糊处（"调成合适大小"）→ 取参考源码的精确值
- 教程的"临时步骤"（如调试用自动开局、事后要删的调用）→ 写成最终行为："启动进入标题画面，不自动开始游戏"
- 教程没写的默认值 → 从参考实现补（动画 FPS、缩放、碰撞尺寸等）
- 无参考源码时：含糊值取合理默认并明确标注（"数值为合理默认，可自行调整"），或与用户确认后再写死
- 明确写出的隐含要求：启动场景设置、新局清场机制、碰撞事件每局只触发一次、怪物互不碰撞

### 4. 撰写题目

按下方模板产出单文件 markdown。输出语言与用户/项目语境一致（界面文本保留原文）。目标引擎已知且有参考源码时，附录写该引擎的映射；目标引擎未知时，核心保持引擎无关，附录写参考实现所用的引擎。

### 5. 自查

- [ ] 规格表里没有引擎术语（"stretch: canvas_items + keep" 这类要改成行为描述，引擎配置挪进附录）
- [ ] 没有任何"需要猜"的数值；换一个引擎实现，完整流程都走得通
- [ ] 验收清单覆盖完整游戏循环（开局 → 移动 → 生成 → 计分 → 碰撞 → 重开）
- [ ] 附录与核心一致：核心里出现的每个值附录里也有
- [ ] 踩坑点清单（格式兼容、元数据文件、物理回调、循环音频）已核对

## 输出模板

```markdown
# {游戏名} — 游戏开发题目

> 实现前请通读全文。规格以第 4 节为准，验收以第 5 节为准。
> 引擎为 {引擎名} 时参考附录 A；其他引擎请自行映射第 4 节规格。

## 1. 游戏概述
一句话玩法 + 目标画面引用 + 关键约束（单人/无胜利条件/界面文本语言）。

## 2. 交付要求
项目放哪里（如 src/<引擎名>/）、可直接运行、资产来源、不得联网下载、
启动时进入标题画面不自动开始。资产未提供时注明需自行生成及风格约束。

## 3. 资产清单
| 文件 | 用途 |

表：资产文件 → 用途；注明编辑器元数据文件不要复制、许可证随附。

## 4. 游戏规格
### 4.1 画面与窗口   （视图尺寸、缩放行为、背景）
### 4.2 输入          （动作 → 按键）
### 4.3 {玩家}        （参数表：速度/出生点/动画/帧率；规则列表）
### 4.4 {怪物}        （参数表 + 生命周期、互不碰撞等规则）
### 4.5 主场景与游戏流程 （计时参数表 + 状态机步骤）
### 4.6 HUD          （如适用：各控件、文本原文、字号、布局）
### 4.7 音频          （BGM 循环、音效时机）

## 5. 验收标准（自测清单）
- [ ] 可运行验证的行为条目…（覆盖完整游戏循环）

## 6. 实现提示（引擎无关）
碰撞方案（触发器/刚体）、物理回调规则、生成方向算法、清场机制、
显示缩放比例、音频格式兼容等踩坑预判。

## 附录 A：{引擎名} 实现参考
场景树（缩进树 + 关键参数注释）、输入映射、脚本要点（伪代码级）、
信号/事件连接表。
```

## 落地与收尾

- 输出位置：通常放项目文档目录（如 `docs/prd/README.md`），命名要易发现。
- 替换旧教程文件前与用户确认（git 历史可恢复）；可复用的资源（如预览 gif）保留并在题目中引用。
- 完成后向用户汇报：删掉了什么废话、补齐了哪些数值、含糊处以哪份为准、留下了哪些踩坑提示。
